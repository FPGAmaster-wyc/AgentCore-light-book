Firmware v0.5.8-jl-breath-bright

This API applies to devices shipped on or after 1 October 2026. Devices shipped earlier have older factory firmware and do not support the API described in this manual; if you need it, contact after-sales support to find out whether the firmware can be upgraded.

The sleep settings in section 15 require firmware v0.5.3 or later; on earlier firmware those two commands are treated as unknown commands.

Compatible firmware: v0.5.3-jl-sleep, AC696N / BR25. This API is the text protocol in the firmware, usable over the USB CDC serial port or Bluetooth Classic SPP/RFCOMM; for the Python client example, see the download entry at the top of this page. v0.5.1 added button queries, subscription and short-press takeover within a session (section 14); v0.5.3 added the settings and reporting for standby sleep and auto power-off (section 15).

You can control the red, yellow and green lights independently, and use blinking, breathing, fading, custom step sequences and buzzer tones; no firmware change is needed for each new use case.

#1. Wiring, connection and first test

#USB serial

  1. Press and hold the button to power the device on, then short-press it to switch to serial mode.
  2. Connect a USB cable that supports data transfer, and find the device’s COM port.
  3. Close the AgentCore desktop service or serial terminal that is holding this COM port.
  4. Your program opens the serial port at 115200 baud, 8 data bits, no parity, 1 stop bit, and sends HELLO\n.
  5. The device replies HELLO:OK; after that you can send API1 commands.

#Bluetooth SPP

  1. The device starts in Bluetooth mode by default; pair AgentCore-Light in Windows Settings.
  2. Find and open the outgoing COM port of the device’s JL_SPP service. Earlier examples use COM49; the actual port is whatever your computer shows.
  3. It uses the same text protocol as USB. The Windows audio connection is not itself an SPP data channel — you must open the matching SPP port.

The firmware’s existing BLE data entry point also feeds the same parser, but the examples in this manual use the USB/SPP serial port. The device’s operating mode is still switched with the button.

#Python quick check

Unzip the examples downloaded from the top of this page and run the following inside the AgentCore-API directory:

powershell
py -3 -m pip install pyserial
py -3 agentcore_api.py --port COM49
py -3 agentcore_api.py --port COM49 --demo

The first invocation only queries capabilities, settings and battery; --demo takes control, lights green, yellow and red for one second each, gives one short beep, and then releases control. Light brightness and the buzzer are still limited by the settings stored on the device.

#2. Text format and replies

A single command line is formatted like this:

text
API1 ID=1 TOKEN=42 LED.SET R=0 Y=0 G=300
  • The line above must end with a newline \n; \r, \r\n and a semicolon ; are also accepted.
  • API1, command names and parameter names are upper-case. Parameters are separated by spaces or tabs; JSON, quotes and Chinese characters are not used.
  • ID is required and ranges from 1 to 65535; you assign the number for each call. Parameter order does not matter.
  • A line is at most 255 bytes, not counting the terminator; unknown parameters, repeated parameters and malformed numbers raise an error.
  • Split and coalesced packets are supported. One receive does not have to equal one command; an over-long line is dropped in full, and its tail is not executed.
  • Send one command, wait for the reply with the same ID, then send the next; the device queue holds up to 8 commands.

Success and failure replies:

text
API1 ID=1 OK
API1 ID=1 ERR CODE=INVALID_ARGUMENT

INFO, STATUS and SOUND.LIST may return extra data lines first, with the OK for the same ID last. The device also sends battery telemetry, replies from the older protocol and asynchronous events; sort them by prefix and ID.

OK means the device’s scheduled task has executed the command — it does not mean the scene has finished playing. A long scene reports completion through the SCENE_DONE event. When the queue is full, or an over-long line makes the request number impossible to extract reliably, the error is returned with ID=0.

#3. Control sessions

Queries need no control ownership. Light, sound, scene and settings writes must open a session first:

text
API1 ID=1 TOKEN=42 SESSION.OPEN LEASE_MS=30000

TOKEN is chosen by you and ranges from 1 to 65535. It is a session number that keeps several control programs from taking the device from one another; it is not a password. LEASE_MS defaults to 30000 and ranges from 1000 to 600000.

Later writes use the same TOKEN. A takeover request with a different TOKEN returns BUSY; opening again with the same TOKEN renews the lease.

text
API1 ID=2 TOKEN=42 SESSION.KEEPALIVE
API1 ID=3 TOKEN=42 SESSION.CLOSE

A session write command that executes successfully renews the lease; ordinary queries do not. Send KEEPALIVE every 10 seconds, or use the example client, which renews automatically.

While custom control is active, the old status/light/sound commands return ERR API_BUSY. Old queries and device preferences still work. The low-battery idle reminder does not override custom output.

Session CLOSE, lease timeout, loss of the SPP/BLE data connection, USB disconnect, power-off or a mode switch stops custom output. After an explicit release or a detected disconnect, the device goes back to its existing connection-waiting/IDLE indication rules. When a USB application closes the port, CDC does not necessarily produce a reliable close event, so send CLOSE or the old HOST_DISCONNECT command; otherwise the session timeout catches it.

While the device is powered off it accepts no API output control, and there is no way to power it on through the API.

#4. Query commands

Examples:

text
API1 ID=10 INFO
API1 ID=11 SETTINGS.GET
API1 ID=12 POWER.GET

POWER.GET: VBAT is in units of 0.01 V; PER is a percentage estimated from voltage; CUR is the target in mA from the charging configuration, not a reading from an external ammeter.

In STATUS, OUTPUT R/Y/G are logical outputs from 0 to 300, before the master brightness and channel calibration are applied; EFFECT is 0 steady on, 1 blink, 2 breathe, 3 fade. FREQ indicates a direct API tone and preset melodies are not reported note by note. PLAYING only says whether a scene is playing.

#5. Basic control of the three lights

text
API1 ID=20 TOKEN=42 LED.SET R=300 Y=0 G=0
API1 ID=21 TOKEN=42 LED.SET R=0 Y=150 G=300
API1 ID=22 TOKEN=42 LED.SET R=0 Y=0 G=0

R/Y/G are each 0 to 300 and default to 0 when omitted; one command sets all three channels in full, so omitted channels do not keep their previous values. Several of the individual lights can be on at once, but they cannot be blended into the colour of a single RGB light.

DURATION_MS is optional; 0 means hold until the next command or the end of the session, and a non-zero value ranges from 20 to 60000 and turns all three lights off when it expires:

text
API1 ID=23 TOKEN=42 LED.SET G=300 DURATION_MS=1000

API channel levels are relative intensities; the master brightness and the existing channel calibration are still applied on top. Master brightness defaults to 30/300, about 10% of full output; at that setting R=300 is roughly 10% PWM on the red light, and R=150 about 5%. The green light’s existing 65% calibration still applies.

The underlying PWM has 100 output steps, so after conversion some neighbouring levels of the logical 300-step scale come out identical; very low levels may round to 0. API1 changes neither the PWM timer frequency nor the hardware resolution.

#6. Parameterised light effects

Use LED.EFFECT; R/Y/G work the same as in LED.SET:

EFFECTParametersBehaviour
SOLIDDURATION_MS optionalSteady on, the same as LED.SET
BLINKON_MS, OFF_MS, each defaulting to 500, range 20–60000Alternates on and off, with custom on and off durations
BREATHEPERIOD_MS defaults to 2000, range 40–60000Triangular brightness curve: dim → bright → dim
FADEDURATION_MS required, 20–60000Fades from the currently displayed value to the target and holds the target when it finishes

For BLINK/BREATHE/SOLID, a DURATION_MS of 0 runs continuously and a non-zero value turns the lights off when it expires; for FADE, DURATION_MS is the transition time.

text
API1 ID=30 TOKEN=42 LED.EFFECT EFFECT=BLINK R=300 ON_MS=200 OFF_MS=800
API1 ID=31 TOKEN=42 LED.EFFECT EFFECT=BREATHE G=300 PERIOD_MS=3000
API1 ID=32 TOKEN=42 LED.EFFECT EFFECT=FADE Y=300 DURATION_MS=1000

LED commands do not cancel a buzzer that is playing on its own. If a combined light-and-sound scene is playing, however, a new LED or buzzer control command cancels the whole scene, so that two sets of execution logic do not contend for the same peripherals.

#7. Buzzer

text
API1 ID=40 TOKEN=42 BUZZER.TONE FREQ=2700 VOLUME=50 DURATION_MS=200
API1 ID=41 TOKEN=42 BUZZER.STOP
API1 ID=42 TOKEN=42 SOUND.PLAY NAME=CLASSIC LOOP=0
  • FREQ is required for TONE: 0 is silent, and non-zero values range from 95 to 10000 Hz. 2700 Hz suits the current buzzer; actual loudness varies with frequency.
  • VOLUME defaults to 100 and ranges from 0 to 100, as a proportion of the master volume; DURATION_MS defaults to 200 and ranges from 20 to 60000.
  • The device’s master volume defaults to 10; a relative value of 50, for example, means using half the master volume. The master switch off, a master volume of 0, or a relative volume of 0 all mean silence.
  • For a direct API tone, when both the master volume and the relative volume are 100, the PWM duty cycle is capped at 50%. Volume percentages are neither decibels nor linear sound pressure.
  • For a preset SOUND, LOOP defaults to 0 and 1 means loop, still bounded by the session lease. Preset sounds use the existing volume and tempo logic.
  • BUZZER.STOP cancels a combined scene that is running; when it stops a standalone sound, standalone light effects are kept.

The current preset names are available through SOUND.LIST, including CLASSIC, UP, DOWN, OK, ALERT, SOFT, CHIME, POP, DONE, and melodies such as MELODY_RISE and MELODY_HAPPY. Do not rely on a hard-coded list — your program should query it first.

#8. Custom scenes: upload, then the device plays them automatically

A scene has at most 64 steps, and each step fully specifies the three lights, the light effect, the sound and the duration. Lights and sounds not set in a step default to off.

The flow is BEGIN → STEP (once per step) → COMMIT → PLAY. Wait for the ACK of each command before sending the next.

text
API1 ID=50 TOKEN=42 SCENE.BEGIN COUNT=4
API1 ID=51 TOKEN=42 SCENE.STEP INDEX=0 G=300 DURATION_MS=1000
API1 ID=52 TOKEN=42 SCENE.STEP INDEX=1 Y=300 DURATION_MS=1000
API1 ID=53 TOKEN=42 SCENE.STEP INDEX=2 R=300 DURATION_MS=1000
API1 ID=54 TOKEN=42 SCENE.STEP INDEX=3 FREQ=2700 VOLUME=50 DURATION_MS=200
API1 ID=55 TOKEN=42 SCENE.COMMIT
API1 ID=56 TOKEN=42 SCENE.PLAY REPEAT=1
  • COUNT is 1 to 64; INDEX starts at 0.
  • STEP accepts R/Y/G, EFFECT, ON_MS, OFF_MS, PERIOD_MS, FREQ and VOLUME, with the same meanings as above. DURATION_MS is required on every step, 20 to 60000.
  • The same INDEX can be re-sent to overwrite it; COMMIT is only possible once every INDEX is present. Invalid parameters do not modify steps already received.
  • BEGIN and STEP go into a pending buffer and nothing plays while you upload. The scene is only replaced after COMMIT has validated everything.
  • You can upload the next scene while one is playing, but COMMIT returns SCENE_RUNNING; send CANCEL first, or wait for the current playback to finish.
  • REPEAT defaults to 1 and ranges from 0 to 1000; 0 loops indefinitely and needs the lease to be renewed.
  • When a finite playback finishes, the three lights and any direct tone are turned off, and the session still belongs to you so that the next operation can be sent. Use SESSION.CLOSE to restore the connection/IDLE indication.
  • Scenes are kept in RAM; closing the session, switching modes or restarting loses them, and they have to be uploaded again.
  • The execution tick is about 20 ms, suited to status lights and notification sounds, not to microsecond-level timing.

Start/completion/cancellation events:

text
API1 EVENT=SCENE_STARTED TOKEN=42 PLAY_ID=56
API1 EVENT=SCENE_DONE TOKEN=42 PLAY_ID=56
API1 EVENT=SCENE_CANCELLED TOKEN=42 PLAY_ID=56

PLAY_ID is the request ID that started that playback; use it to tell different playbacks in the same session apart.

Alternating blink: upload two steps, red on and yellow on, then set REPEAT=0. Custom melody: upload FREQ/VOLUME/DURATION_MS for each note, using FREQ=0 for a rest step. Light and sound in sync: set the light parameters and FREQ in the same step.

#9. Stopping and device configuration

text
API1 ID=60 TOKEN=42 SCENE.CANCEL
API1 ID=61 TOKEN=42 OUTPUT.STOP
API1 ID=62 TOKEN=42 SETTINGS.SET BRIGHTNESS=30 BUZZER=1 VOLUME=10 LOW_BATTERY_ALERT=1 SAVE=1

SCENE.CANCEL stops the current scene and turns its output off; with no scene it leaves standalone lights and sounds alone. OUTPUT.STOP stops all custom lights and sounds, keeping the session and the committed scene.

SETTINGS.SET accepts:

ParameterRangeDescription
BRIGHTNESS0–300Master brightness, default 30
BUZZER0/1Master buzzer switch
VOLUME0–100Master volume, default 10
LOW_BATTERY_ALERT0/1Low-battery idle reminder
SAVE0/1, default 00 changes only the running value; 1 saves the device settings after a delay of about 1 second

Omitted settings keep their current values. SAVE=1 can also be sent on its own to save the whole current configuration. A save uses the snapshot taken when the request was made; wait until you see the legacy-format SETTINGS:...STORE:VM receipt before cutting power. Several saves in quick succession are merged into the last request.

Temporary settings are not restored automatically by SESSION.CLOSE; after a power cycle the device restores them from device storage. Scenes and individual playbacks are not written to flash.

#10. Python client example

Put the downloaded agentcore_api.py in the same directory as your script:

python
from agentcore_api import AgentCoreAPI

with AgentCoreAPI("COM49") as api:
    print(api.request("INFO"))
    api.acquire()  # renewed automatically
    api.effect("BREATHE", green=300, PERIOD_MS=2000)
    api.tone(frequency=2700, volume=50, duration_ms=200)

    api.play_scene([
        {"G": 300, "DURATION_MS": 1000},
        {"Y": 300, "DURATION_MS": 1000},
        {"R": 300, "FREQ": 2700, "VOLUME": 50, "DURATION_MS": 200},
    ], repeat=1)
    print(api.wait_scene(timeout=10))
    # leaving the with block releases the session and closes the port

In your own agent or application code, simply call api.led, api.effect or api.play_scene when an event occurs. The list returned by a query contains every API data line for that request; device errors raise APIError.

This delivery implements the firmware protocol and the Python serial client. The existing software’s HTTP /command uses a single-slot pending-send path, so it cannot guarantee that all the commands of a multi-command scene upload are kept, and it does not wait for the full API1 receipt; do not upload scenes through rapid successive HTTP POSTs for now. A new HTTP SDK / web developer entry point needs separate work later — do not treat the text protocol here as an HTTP route that has already been added.

#12. On-device acceptance testing

  1. Confirm that the old IDLE/BUSY/DONE/ERROR states, button power on/off and mode switching still work.
  2. Run the Python --demo and confirm that green, yellow and red each light for one second, then a short beep sounds, and the connection state is restored.
  3. Verify BLINK, BREATHE and FADE, plus scene looping and rests between notes.
  4. Call the short beep 100 times in a row and check that it never stops working; with the master switch OFF or the master volume at 0 there should be complete silence.
  5. While playing, unplug the cable or drop the SPP connection, or stop renewing the lease, and check that output stops and the waiting/IDLE indication returns.
  6. After sending SAVE=1, wait for the save receipt before restarting, and confirm the settings come back; a SAVE=0 change should not become part of the next boot configuration.
  7. Set IDLE_SLEEP_SEC to 60 and, after one minute idle, confirm that all lights are off, the connection is still up and a status command brings the lights back automatically; set BT_DISCONNECT_OFF_SEC to 60, drop the Bluetooth data connection for one minute and confirm that the device powers itself off.

#13. Upgrade notes

This firmware version enlarges the application area, and the configuration storage layout differs from older versions.

Before upgrading, read and record the master brightness, buzzer switch, master volume and low-battery reminder settings with the old software; after upgrading, check those settings and the Bluetooth pairing again, and restore the settings and re-pair if necessary.

SAVE=1 can save settings to the device, but old data is not guaranteed to carry over automatically across different configuration layouts — record any settings you need to keep before upgrading.

From v0.5.3 onwards, the firmware migrates the settings from the old layout automatically during an upgrade (master brightness, buzzer switch, master volume, low-battery reminder), so these no longer have to be set by hand afterwards; it is still worth checking them after the upgrade, and confirming against section 15 that the defaults of the two sleep times are what you expect.

#14. Button queries, subscription and short-press takeover (added in v0.5.1)

The device has only one physical button (currently PB6 in the board configuration, active low). The API’s button control only affects short presses after power-on; it cannot disable long-press power-off, and the API cannot power the device on. The existing 50 ms scan and roughly 3-second long-press power on/off logic are unchanged.

#14.1 Default mode and takeover mode

ModeShort press after power-onLong press of about 3 seconds
DEFAULT (default)Switches between Bluetooth and USB serial modeKeeps the original power on/off behaviour
APPLICATION (API takeover)Does not switch transport mode; after subscription it reports CLICK, and your program decides what it is used forKeeps the original power-off behaviour; the API cannot disable it
  • The device is in DEFAULT with no subscription each time it starts and when a new API session is established. SESSION.OPEN on its own does not take over the button.
  • Opening an existing session again with the same TOKEN only renews the lease; it does not reset the selected button mode or subscription. Only a session established again after release returns to the default.
  • APPLICATION belongs only to the current control session and is not written to flash/VM. SESSION.CLOSE, lease timeout, loss of the data connection, power-off and a transport-mode switch all restore DEFAULT and cancel the subscription; the next connection has to OPEN, SUBSCRIBE and set MODE again.
  • Recovery from a disconnect follows the device actually detecting that the link went down. Closing a USB COM port may produce no reliable disconnect event, so send CLOSE on a normal exit; after an abnormal exit the lease timeout catches it, and an immediate recovery after closing the port is not guaranteed.
  • Whether the button is taken over and whether it is subscribed are independent of each other: ENABLE=0 only stops reporting, it does not restore the mode. While in APPLICATION, a short press still does not switch modes even with no subscription. To restore physical mode switching, send MODE=DEFAULT or close the session.
  • A short press does not renew the lease; SESSION.KEEPALIVE is still needed. The Python client’s acquire() starts automatic renewal.

#14.2 Commands and responses

Query (no session needed, does not renew the lease):

text
API1 ID=100 BUTTON.GET
API1 ID=100 OK PRESSED=0 MODE=DEFAULT SUBSCRIBED=0 OWNER=0

PRESSED=1 means the scan sees the button held down and 0 means released, with an update granularity of about 50 ms; it is not an interrupt-level instant reading. MODE is what a short press does, SUBSCRIBED says whether the current session is subscribed, and OWNER is the session TOKEN or 0.

Take a control session first, then subscribe and switch to takeover mode. Wait for the OK with the matching ID after each command before sending the next:

text
API1 ID=101 TOKEN=42 SESSION.OPEN LEASE_MS=30000
API1 ID=102 TOKEN=42 BUTTON.SUBSCRIBE ENABLE=1
API1 ID=103 TOKEN=42 BUTTON.MODE MODE=APPLICATION

ENABLE is required for BUTTON.SUBSCRIBE and is 0 or 1; MODE is required for BUTTON.MODE and accepts only the upper-case values DEFAULT and APPLICATION. Both must use the current session TOKEN; on success the device replies OK under the matching ID and renews the lease. Invalid parameters return INVALID_ARGUMENT; no session or a TOKEN that does not match return NO_SESSION / NOT_OWNER respectively.

After a valid short press is released, the device reports on its own:

text
API1 EVENT=BUTTON TOKEN=42 ACTION=CLICK SEQ=1 HELD_MS=150 MODE=APPLICATION
  • TOKEN is what you filter events from your own session by; this line has no request ID — it is an unsolicited event, not a command receipt.
  • Only CLICK is provided today; there is no DOWN, UP, double-click or LONG_PRESS. A long press that powers the device off does not also produce a CLICK.
  • HELD_MS is the hold time accumulated by the firmware’s scan, in ms; its accuracy is affected by the 50 ms scan.
  • SEQ is the short-press sequence number for this run; it starts again after a restart and the 32-bit counter can wrap. It can also increment while you are not subscribed and is not required to be contiguous; do not treat it as a permanent identifier across restarts.
  • You can subscribe to CLICK in DEFAULT too, but the short press then switches transport mode and drops the current link, so the event may not arrive. When the short press has to drive your own application logic reliably, use APPLICATION.
  • Power-off and disconnects do not guarantee that the last event arrives. Your program must handle serial-port closure, connection errors and session timeouts; do not rely on button events alone to tell whether the device is powered off.

Restoring the default button use explicitly (both commands can be run in the current session):

text
API1 ID=104 TOKEN=42 BUTTON.MODE MODE=DEFAULT
API1 ID=105 TOKEN=42 BUTTON.SUBSCRIBE ENABLE=0

This does not leave the LED/buzzer API session. If you also want the device’s original connection/IDLE light effects back, send SESSION.CLOSE afterwards.

#14.3 Python example

Close the desktop service that holds the COM port, then run:

powershell
py -3 agentcore_api.py --port COM49 --button-demo

The script takes over short presses and waits up to 30 seconds. A short press then prints the event and lights the green light for one second, after which the script restores DEFAULT, unsubscribes and releases the session; a long press still powers the device off, which may make the example report a connection error or timeout — that is not a short-press event. Replace COM49 with the actual USB CDC or Bluetooth outgoing port.

For your own application code:

python
import time
from agentcore_api import AgentCoreAPI

with AgentCoreAPI("COM49") as api:
    api.acquire()
    api.button_subscribe(True)
    api.button_mode("APPLICATION")
    print(api.button_get())
    print("Short-press the device button")
    event = api.wait_button(timeout=30)
    print(event)
    api.tone(frequency=2700, volume=50, duration_ms=200)
    api.led(green=300, duration_ms=1000)
    time.sleep(1)  # hold the session until the output is done, or leaving the with block stops the light and buzzer at once
    # carry on with your own logic here; leaving the with block releases the session and restores the default button mode.

wait_button() and wait_scene() consume the same event queue, so do not run them at the same time or let several threads fight over events. When you need to handle scenes, button events and so on together, read api.events in one place and dispatch by EVENT in a single application thread. The on_event callback runs on the serial reader thread and must not call reply-waiting methods such as api.request()/led()/tone() directly, or it blocks the reader; hand events to your application thread through your own thread-safe queue instead.

#14.4 On-device testing

  1. With no API session running, a short press should switch between Bluetooth and serial as usual, and a long press of about 3 seconds should still power the device off.
  2. With only OPEN sent and no BUTTON.MODE, a short press still switches modes.
  3. Run --button-demo: a short press delivers a CLICK and the transport does not switch.
  4. In APPLICATION, press repeatedly and check that one release produces exactly one CLICK; a long press to power off produces no CLICK.
  5. Set ENABLE=0: short presses are no longer reported, but the device is still in APPLICATION; after setting MODE=DEFAULT, short presses switch modes again.
  6. Close the session, unplug USB or drop the SPP connection, or stop renewing the lease: the next short press goes back to the default behaviour. When a session is established again, GET should show DEFAULT and SUBSCRIBED=0.
  7. Set the takeover and then restart: check that the device is still in DEFAULT — the takeover mode is not saved to the device.

#15. Standby sleep and auto power-off (added in v0.5.3)

The device has two power-saving actions, and the timing of both can be changed:

SettingDefaultDescription
IDLE_SLEEP_SEC600 secondsAfter this much continuous idle time, all status lights go out and the device enters sleep. The connection stays up, and a new status command wakes it automatically
BT_DISCONNECT_OFF_SEC300 secondsBluetooth mode only: after this much time with no data connection, the device powers itself off. It powers off even while USB charging is plugged in

Both range from 0 to 3600 seconds, and 0 disables the matching automatic action; a setting is written to device storage after about 1 second and stays in effect after being powered on again.

These two settings have no matching API1 command; use the legacy-format text commands (the same channel as settings such as BRIGHTNESS, with no API1 prefix, and a \n terminator just like the rest):

text
IDLE_SLEEP_SEC:600
BT_DISCONNECT_OFF_SEC:300
  • The value must be a plain number; above 3600 the device replies ERR IDLE_SLEEP_SEC / ERR BT_DISCONNECT_OFF_SEC, and on success it returns one line, SLEEP_SETTINGS:....
  • While a session is open, the device only lets queries and a subset of the settings commands through, and these two are answered with ERR API_BUSY; to change them, send SESSION.CLOSE first, or use a channel with no session open.
  • Query with GET_SETTINGS (also available while a session is open); the device returns one extra line:
text
SLEEP_SETTINGS:IDLE_SLEEP_SEC:600,BT_DISCONNECT_OFF_SEC:300,SLEEP:OFF,STORE:VM

SLEEP:ON means the device is currently in lights-off sleep.

While asleep, all lights are off, and the Bluetooth/serial connection and button scanning stay active; after a new status command (IDLE, BUSY and so on) the light effects come back immediately. The idle-state green light is a low-brightness breathing effect; setting IDLE_SLEEP_SEC to 0 turns the automatic lights-off off, and the idle state then keeps breathing instead of going completely dark.

The device does not enter sleep while an API session is open; once the session is released, the idle timing starts again. Sleep is managed by the firmware’s state machine, and custom API light effects are unaffected.
